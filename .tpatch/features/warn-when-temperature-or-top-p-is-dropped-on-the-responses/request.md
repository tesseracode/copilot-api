# Feature Request: Warn when temperature or top_p is dropped on the Responses path, and document the asymmetry. translateRequestToResponses builds a strict allowlist that never carries temperature or top_p, so a client that sets them on a Responses-routed model gets them silently ignored while the same request against a Chat-routed model has them forwarded verbatim. A live probe confirms upstream still rejects them: temperature 0.2 returns 400 Unsupported parameter on every Responses model tested, and top_p 0.5 is rejected by gpt-5.4-mini, gpt-5.4, gpt-5.5 and gpt-5.6-luna but accepted by gpt-5.3-codex. Notably temperature 1 is accepted, so dropping the default value is a semantic no-op. Forwarding is not viable because it would turn currently succeeding requests into 400s, and per-model forwarding is not viable because the catalog advertises no temperature or top_p capability at all, so any allowlist would be a hardcoded heuristic that goes stale. Emit a single warning per request naming the model and the dropped parameters, only when the value is not the default of 1, and document the behavior and the Chat versus Responses asymmetry in the README.
