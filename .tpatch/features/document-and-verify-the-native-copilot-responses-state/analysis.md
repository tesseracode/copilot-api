# Analysis

Two independent consumers have now failed against this proxy over Responses state: Hermes Agent, and VS Code Copilot Chat via a custom endpoint, which returned `400 {"code":"invalid_request","message":"store must be the boolean false when provided"}`. That repetition makes the state contract a real compatibility question rather than a one-off client bug.

The measured upstream contract is stateless. A direct synthetic control shows `store:true` rejected with HTTP 400 `unsupported_value` while `store:false` succeeds. Because upstream does not retain responses, `previous_response_id`, conversations, background responses, and the Responses lifecycle endpoints cannot be honestly promised. `tests/operational-hardening.test.ts` already pins that `/v1/responses/<id>`, `/responses/<id>`, and `/v1/conversations` return 404, so the proxy does not currently advertise the operations it cannot fulfill.

The proxy path is already correct. `src/routes/responses/route.ts` validates only `model` and the type of `stream`, then re-marshals the parsed payload, so `store` and `previous_response_id` pass through untouched in both directions; `tests/native-responses-route.test.ts` already proves arbitrary request/response field preservation and upstream status/request-ID forwarding. No reproducible proxy defect exists here.

Emulation would be unsafe and expensive. Silently coercing `store:true` to `false` is the most tempting fix and the worst one: a client that believes the provider retained state may then send only `previous_response_id` with truncated history, producing a silently wrong conversation rather than a loud 400. Genuine proxy-side persistence would require ownership, retention, encryption, cleanup, concurrency, and multi-instance consistency, and would still not make upstream stateful. Suppressing the field would equally hide a contract mismatch the client must resolve.

Client-side resolution is already proven. The pinned gateway canary (`tesseragateway@cf8b650`, `docs/evidence/vscode-responses-compatibility/2026-08-13.md`) certifies VS Code 1.133.0 with Copilot Chat 0.61.0 on `copilot/gpt-5.6-sol` once `zeroDataRetentionEnabled: true` makes the client send `store:false`. The earlier failure therefore came from client configuration and pre-fix gateway behavior, not from a missing stateful implementation here. The related tool-continuation failure was likewise proven gateway-owned — its 10s Responses timeout — and fixed there, with continuation succeeding at ~13.7s and ~11.3s afterwards; no copilot-api tool-call change is justified without a local reproduction.

The remaining gap is documentation and regression protection, not code: the repository never states that its Responses contract is stateless full-history replay, never distinguishes upstream response storage from proxy usage accounting (`copilot_usage`, which is unrelated to `store`), and has no test pinning `store`/`previous_response_id` forwarding against future well-intentioned coercion.
